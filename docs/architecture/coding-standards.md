# Coding Standards

1. **Context7 First**
   - Before starting any work, always use Context7 to gather context about the technologies, libraries, and frameworks involved in the task. This ensures you have up-to-date, relevant information and best practices.
   - Example: Use Context7 to review docs or API usage before implementing or modifying code.

2. **Use `npx` for Commands**
   - Always use `npx` to run CLI commands. This guarantees you're using the correct, project-local version of tools and avoids global version mismatches.
   - Example: `npx nx build my-app` instead of `nx build my-app`.

3. **Repository Interaction via Nx**
   - All repository interactions (building, testing, generating code, etc.) must be performed using Nx commands.
   - For creating new components, modules, or other code artifacts, always use Nx generators (`npx nx generate ...`).
   - Do not manually create files or folders that can be generated by Nx.

4. **Prettier Compliance**
   - All code must comply with the project's Prettier configuration. Run Prettier before committing code, and ensure your editor is set up to auto-format on save.
   - Example: `npx prettier --write .`

5. **Angular Material V3**
   - Prefer Angular Material components where applicable. When not applicable, use standard HTML elements and style them appropriately.

6. **SCSS over CSS**
   - use sass instead of css for angular components.
   - never use tailwind classes

# Additional Coding Standards (Architecture-Driven)

1. **Feature-Based Structure & Shared Libraries**
   - Enforce feature-based folder structure for both frontend and backend.
   - All reusable UI components must go in a shared library (e.g., `libs/ui/`).
   - Shared interfaces/types must live in a dedicated shared library (e.g., `libs/shared-interfaces`).

2. **State Management**
   - Use RxJS-based services for state in Angular unless/until complexity justifies NgRx.
   - Document when/how to escalate to centralized state management.

3. **Repository Pattern**
   - Backend must use the repository pattern for all data access.
   - No direct DB queries in services/controllers—only in repositories.

4. **API & Auth**
   - All API endpoints must be RESTful and follow consistent naming conventions.
   - Use JWT for authentication; never bypass guards.

5. **Testing**
   - All code must have unit tests; use Nx to run and enforce coverage.
   - E2E tests must be written in Playwright for critical user flows.

6. **CI/CD & Linting**
   - All PRs must pass Nx lint/test/build before merge (enforced by CI).
   - Linting and formatting must be automated in CI (GitHub Actions).

7. **Docker & K8s**
   - All deployable code must have a Dockerfile and be runnable in K8s.
   - No hardcoded config—use ConfigMaps/Secrets.

8. **TypeScript**
   - Strict mode must be enabled.
   - No `any` types except in legacy code with TODO to refactor.

9. **Documentation**
   - All public modules, services, and components must have doc comments.
   - Update architecture docs when making significant changes.

10. **Security**
    - Never commit secrets; use K8s Secrets.
    - Validate all inputs, especially in API endpoints.

11. **Dependency Management**
    - Use Nx to manage dependencies; no direct package installs in app folders.

12. **CSS/Styling**
    - Use SCSS only; no plain CSS.
    - Follow BEM or a documented naming convention.

13. **Helm/Infra**
    - All infra changes must be reflected in Helm charts.
    - No manual K8s resource creation outside Helm.

14. **Tilt for Local Dev**
    - Use Tilt for local K8s orchestration; document Tiltfile changes.
