# Coding Standards

1. **Context7 First**
    - Before starting any work, always use the Context7 mcp server to gather context about the technologies, libraries, and frameworks involved in the task. This ensures you have up-to-date, relevant information and best practices.
    - Example: Use Context7 to review docs or API usage before implementing or modifying code.

2. **Use `npx` for Commands**
    - Always use `npx` to run CLI commands. This guarantees you're using the correct, project-local version of tools and avoids global version mismatches.
    - Example: `npx nx build my-app` instead of `nx build my-app`.

3. **Repository Interaction via Nx**
    - All repository interactions (building, testing, generating code, etc.) must be performed using Nx commands.
    - For creating new components, modules, or other code artifacts, always use Nx generators (`npx nx generate ...`).
    - Do not manually create files or folders that can be generated by Nx.

4. **Prettier Compliance**
    - All code must comply with the project's Prettier configuration. Run Prettier before committing code, and ensure your editor is set up to auto-format on save.
    - Example: `npx prettier --write .`

5. **Angular Material V3**
    - Prefer Angular Material components where applicable. When not applicable, use standard HTML elements and style them appropriately.

6. **SCSS over CSS**
    - ALWAYS use sass instead of css for angular components.
    - NEVER use tailwind classes in templates
    - prefer `rem` instead of `px` for this project 1rem = 16px. Exceptions are - borders use px; media breakpoints use px.

7. **Angular preferences**
    - use OnPush change detection unless default is REALLY needed
    - use new angular template control flow @if @for, NOT ngIf ngFor and the like
    - use signals

    1. **Use Correct Nx Generator**: Always use `@nx/angular:component` for Angular components

        ```bash
        npx nx generate @nx/angular:component --path=apps/jp-aid/src/app/component-name/component-name --standalone=true --changeDetection=OnPush --style=scss --prefix=kl
        ```

    2. **Component Naming**: Follow project conventions
        - Selector prefix: `kl-` (e.g., `kl-kanji-detail`)
        - Class name: PascalCase without suffix (e.g., `KanjiDetail`)
        - File name: kebab-case with type suffix (e.g., `kanji-detail.ts`)

    3. **Signal-Based State Management**: Use signals for reactive state

        ```typescript
        // ✅ Preferred
        private kanjiId = signal<string>('');
        protected kanji = computed(() => this.findKanji(this.kanjiId()));

        // ❌ Avoid
        private kanjiId: string = '';
        protected kanji: Kanji | null = null;
        ```

    4. **Dependency Injection**: Use inject() function in components

        ```typescript
        // ✅ Preferred
        private router = inject(Router);
        private route = inject(ActivatedRoute);

        // ❌ Avoid
        constructor(private router: Router, private route: ActivatedRoute) {}
        ```

    5. **Template Control Flow**: Use modern Angular control flow syntax

        ```html
        <!-- ✅ Modern syntax -->
        @if (kanji(); as kanjiData) {
            @for (reading of kanjiData.readings; track reading) {
            <span>{{ reading }}</span>
            }
        }

        <!-- ❌ Legacy syntax -->
        <div *ngIf="kanji() as kanjiData">
            <span *ngFor="let reading of kanjiData.readings; trackBy: trackByFn">
            {{ reading }}
            </span>
        </div>
        ```

    6. **Change Detection**: Always use OnPush for performance

        ```typescript
        @Component({
            changeDetection: ChangeDetectionStrategy.OnPush // Required
        })
        ```

    7. **Route Configuration Checklist**:
        - [ ] Add component import to `app.routes.ts`
        - [ ] Use consistent URL patterns (`/resource/:id`)
        - [ ] Add animation data for page transitions
        - [ ] Test route parameter extraction

    8. **Route Parameter Pattern**:

        ```typescript
        // ✅ Consistent pattern
        {path: 'kanji/:id', component: KanjiDetail, data: {animation: 'KanjiDetail'}}

        // Navigation usage
        this.router.navigate(['/kanji', kanjiId]);

        // Parameter extraction
        private kanjiId = toSignal(this.activatedRoute.params.pipe(map(params => params['id'] || '')), {initialValue: ''});

        ```

    9. **Template Requirements**:
        - Use semantic HTML with proper accessibility attributes
        - Include loading states and error handling
        - Follow consistent styling patterns
        - Add proper TypeScript strict mode compliance

8. **Templates**
    - for properties on template elements, order properties thus: ids first, class props, inputs, then finally outputs
    - Example: <button #myButton mat-button class="back-button" [text]="textValue" (click)="goBackToSearch()">

9. **Testing**

    1. **Use Jest Syntax Consistently**: Never mix Jasmine and Jest syntax

        ```typescript
        // ✅ Jest (Correct)
        const mockService = {
        method: jest.fn()
        };
        mockService.method.mockReturnValue(data);

        // ❌ Jasmine (Incorrect in Jest environment)
        const mockService = jasmine.createSpyObj('Service', ['method']);
        mockService.method.and.returnValue(data);
        ```

    2. **Mock Setup Pattern**: Use consistent mock object structure

        ```typescript
        let mockRouter: {navigate: jest.Mock};
        let mockActivatedRoute: {params: Observable<any>};

        beforeEach(() => {
        mockRouter = { navigate: jest.fn() };
        mockActivatedRoute = { params: paramsSubject.asObservable() };
        });
        ```

    3. **Change Detection**: Always trigger change detection after interactions

        ```typescript
        // ✅ Correct
        element.click();
        fixture.detectChanges(); // Required for state updates
        expect(element.classList).toContain('active');
        ```

    4. **Required Test Imports**: Always include for Angular Material components

        ```typescript
        import {NoopAnimationsModule} from '@angular/platform-browser/animations';
        // Add to TestBed imports
        ```

10. **properties MUST use camel case**
11. **Fixtures**
    - Use fixtures when you would otherwise create an object literal
    - When creating an interface always create a fixture for easy creation of said interface:

    Example:

    ```./kanji.ts
    export interface ExampleWord {
        readonly kanji: string;
        readonly reading: string;
        readonly meaning: string;
    }
    ```

    ```../testing/kanji.fixtures.ts
        export const exampleWordFixture = (
            kanji: ExampleWord['kanji'],
            reading: ExampleWord['reading'],
            meaning: ExampleWord['meaning']
        ): ExampleWord => ({kanji, reading, meaning});
    ```

# Additional Coding Standards (Architecture-Driven)

1. **Feature-Based Structure & Shared Libraries**
    - Enforce feature-based folder structure for both frontend and backend.
    - All reusable UI components must go in a shared library (e.g., `libs/ui/`).
    - Shared interfaces/types must live in a dedicated shared library (e.g., `libs/shared-interfaces`).

2. **State Management**
    - Use RxJS-based services for state in Angular unless/until complexity justifies NgRx.
    - Document when/how to escalate to centralized state management.

3. **Repository Pattern**
    - Backend must use the repository pattern for all data access.
    - No direct DB queries in services/controllers—only in repositories.

4. **API & Auth**
    - All API endpoints must be RESTful and follow consistent naming conventions.
    - Use JWT for authentication; never bypass guards.

5. **Testing**
    - All code must have unit tests; use Nx to run and enforce coverage.
    - E2E tests must be written in Playwright for critical user flows.

6. **CI/CD & Linting**
    - All PRs must pass Nx lint/test/build before merge (enforced by CI).
    - Linting and formatting must be automated in CI (GitHub Actions).

7. **Docker & K8s**
    - All deployable code must have a Dockerfile and be runnable in K8s.
    - No hardcoded config—use ConfigMaps/Secrets.

8. **TypeScript**
    - Strict mode must be enabled.
    - No `any` types except in legacy code with TODO to refactor.

9. **Documentation**
    - All public modules, services, and components must have doc comments.
    - Update architecture docs when making significant changes.

10. **Security**
    - Never commit secrets; use K8s Secrets.
    - Validate all inputs, especially in API endpoints.

11. **Dependency Management**
    - Use Nx to manage dependencies; no direct package installs in app folders.

12. **CSS/Styling**
    - Use SCSS only; no plain CSS.
    - Follow BEM or a documented naming convention.

13. **Helm/Infra**
    - All infra changes must be reflected in Helm charts.
    - No manual K8s resource creation outside Helm.

14. **Tilt for Local Dev**
    - Use Tilt for local K8s orchestration; document Tiltfile changes.
